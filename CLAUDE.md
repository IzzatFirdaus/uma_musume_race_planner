## 2. The two rules that matter most

### 2.1 Dual storage — branch or lose data

Career runs live in **two** places. Every write path must handle both:

```php
if ($plan->isLocal()) {
    // Server returns a payload/array; the CLIENT persists it.
} else {
    // Server writes to the database.
}
```

This is enforced by **convention only** — there is no repository interface and
no compiler check. The failure mode is silent data loss or duplication, not an
exception. Services that already do this correctly, use as reference:
`PlanService::createQuickPlan()`, `StatProgressService::logTurn()`.

Local runs live in `window.localRunStorage` (browser `localStorage`). The
server holds **no copy**. A lost Local run is gone.

### 2.2 Authorization — currently broken, do not make it worse

`routes/web.php` has no middleware, and `PlanDetailsPage::mount($planId)`
performs no ownership check. `PlanPolicy` is correct but never called.

**Any new route, controller, or Livewire action touching a `Plan` must call
`$this->authorize()` or `Gate::authorize()`.** A Livewire request is a real
HTTP request. Never add a model method that relies on `Plan::booted()`
defaulting `user_id` to 1 — that is the anonymous/public user.

## 5. Livewire conventions

- Namespace is `App\Livewire/**` (not `App\Http\Livewire`).
- All 33 components extend `Livewire\Component` directly — **there is no base
  class or shared trait.** Do not invent one casually; if you add cross-cutting
  behaviour, a trait is safer than a base class.
- Single root element per component view. `wire:key` in every loop.
- `wire:model.live` for live updates — `wire:model` is deferred in Livewire 3.
- Validate in the component (`$this->validate()`) or a Form Request. Never
  trust input.
- Use Alpine **only** for micro-interactions (dropdown, hamburger, transition).
  Anything stateful belongs in Livewire.
- Alpine ships inside Livewire's bundle — do not npm-import `alpinejs`.
- Only these Alpine stores are expected to exist: `connection`, `preferences`,
  `toast`, `keyboard`. **All four are currently missing** — the FOUC guard in
  `components/layout.blade.php` reads a store that isn't there.

## 6. Styling — know which system you're in

**Three layouts coexist and this is a live migration hazard:**

| Layout | System | Used by |
|--------|--------|---------|
| `layouts/app.blade.php` | **Bootstrap 5** (CDN) | dashboard, guide, characters |

**Before adding a class, check which layout renders the page.** A Tailwind
class on a Bootstrap-rendered page is a silent no-op, and vice versa. Do not
add a fourth layout. Consolidating to one is a planned goal.

`tailwind.config.js` defines custom scales — use them rather than raw hex:
`stat.speed|stamina|power|guts|wit`, `grade.SS…G`, `tier.*`, `mood.*`,
`status.*`, `storage.local|account`.

## 7. Data model gotchas

- **`Umamusume` is not a normal model** — string PK, zero relationships, 18
  JSON columns cast to `AsArrayObject`. Filtering is PHP array work, not SQL.
- **`RacePrediction` stat columns are strings** defaulting to `'○'`
  (a "not set" glyph). Never write them as numbers or compare them in SQL.
- **`CareerSnapshot` is immutable** — `updating()` returns false.
- Most child tables set `$timestamps = false`, so you cannot order by recency.
- **Enums:** use the 9 string-backed ones. `RunStatus` and `CareerYear` are
  **dead** — do not use them, and do not add a third status vocabulary
  alongside `plans.status`.
- **Factories exist for 14 models.** `Turn`, `RacePrediction`, and
  `CareerSnapshot` have **none** despite declaring `HasFactory` — build those
  by hand. `SkillFactory` sets a `rarity` attribute that is not a real column.
- `skill_reference` has **46** rows, not 500+, and `name_jp` is `null` for all
  of them. Do not write code assuming a complete bilingual catalog.
